## Context

The 3D downstream package ([ADR 0030](adr-draft-0030-3d-as-downstream-package.md)) needs three things from the core that the package root does not give today. All numbers below were measured on `main@1a1efd9` (462 root export names; the previous reading, `main@98a4156`, had 461 — the one new name is the type `SegmentSelect` from PR #230 — and every symbol below has the same file, line and declaration text at both commits).

1. **The fully resolved plan, including imports.** `compile().ast` is the *unlinked* AST; feeding it to the exported `resolveAll` silently drops imported and placed content (`examples/imports.arch` yields 3 elements, with no diagnostic). The complete path is `resolvePlan(source, { world })` in `src/analyze.ts` (line 99): parse → link → resolve, returning `{ ir: ResolvedPlan | null; diagnostics: Diagnostic[]; levels: ResolvedLevel[] }`. It is **not exported**, and neither are `parse` and `link`.
2. **The wall-joinery seam.** `joinWallSet` (`src/wall-lowering.ts:130`) turns resolved walls and their openings into one joined outline per wall set; its optional third argument `split = { faceOf, faces }` yields the per-wall ownership polygons the 3D package needs (`split.faceOf = (w) => w.id`; verified on 45 plans). `loopsToPolygons` (`src/geometry/joinery.ts:1223`, a `const` arrow function) discretises its exact arc edges. Neither is exported.
3. **The door leaf.** `doorSwing` (`src/geometry.ts:175`) is the one place that turns a door's hinge, swing and host wall into the leaf's pose. Not exported; a downstream copy would be a second implementation of something ADR 0018's principle forbids duplicating (the core already warns, in `joinWallSet`'s own comment, that a second footprint derivation is how a drawing and its extrusion come to disagree).

Why not reach for the sources: the package's `exports` map is `"."` and `"./link"` only, so `@chanmeng666/archlang/dist/analyze.js` cannot be imported by name. Inside the monorepo a relative `../../src/…` import works (the repository's own `playground` test and `mcp-worker` do that for other modules), but it bypasses the published surface and breaks the day the package is extracted or tested against a published core.

The type closure is the other half of the problem. `test/public-surface.test.ts` guards that every type reachable from `describe()`'s result is nameable from `src/index.ts`; nothing guards the signatures above. Deriving the closure the same way the test does — breadth-first over type-reference nodes, signature only, stopping at names the root already exports — finds **14 names that a consumer of these four functions could not write down**: `AnalyzeOptions`, `Arc`, `DoorHinge`, `DoorLike`, `DoorSwing`, `DoorSwingDir`, `Edge`, `EdgeLoop`, `JoinableWall`, `JoinedCut`, `JoinedWallSet`, `JoineryResult`, `JoinerySplit`, `Opening`. (The first derivation, in plan v0.4, listed "10 + 2" — and one of the 10 was the generic parameter `W`, which is not an export — because it did not follow the constraint `W extends JoinableWall` or the `Edge` alias; the real count is 13 types plus `AnalyzeOptions`. `RWall.arcs` already exposes `Arc` through an exported type, so `Arc` is a latent hole today.) `AnalyzeOptions` is `Pick<CompileOptions, "plugins" | "world">`; `CompileOptions`, `World`, `ElementDef`, `ResolvedPlan`, `Diagnostic` and `ResolvedLevel` are already exported.

## Decision

1. **Export four values from `src/index.ts`:** `resolvePlan`, `joinWallSet`, `loopsToPolygons`, `doorSwing`. Each is a plain re-export from the module that declares it (`export { … } from "./analyze.js"` and so on, in a commented block next to the existing `resolveAll` group), so no function body is touched and no import graph changes for `compile()`.
2. **Export the 14 types of the signature closure** (list above), each from the module that declares it: `AnalyzeOptions` (`src/analyze.ts`); `JoinableWall`, `JoinedCut`, `JoinedWallSet` (`src/wall-lowering.ts`); `JoineryResult`, `JoinerySplit` (`src/geometry/joinery.ts`); `Edge`, `EdgeLoop` (`src/geometry/band.ts`); `Arc` (`src/geometry/arc.ts`); `Opening` (`src/ir.ts`); `DoorLike`, `DoorSwing` (`src/geometry.ts`); `DoorHinge`, `DoorSwingDir` (`src/grammar/tokens.ts`). None of the 14 names is exported today, so there is no collision (checked by `export_closure_refs.mjs`).
3. **Export the eight element-type names (C2)** that `ResolvedElement` already carries but does not name: `ROpening`, `RStair`, `RElevator`, `REscalator`, `RRoof`, `RVoid`, `ROutdoor`, `RFence`. Pure types, zero runtime effect; without them a consumer writes `Extract<ResolvedElement, { kind: "stair" }>`, which works but is not stable against a rename of the discriminant. (Measured: the union `ResolvedElement` has nine members the root does not name — these eight plus `RWallsFromRooms`, the ADR 0028 statement element, which the adapter does not need because derived walls are already in `ir.walls`. The owner accepted the list of eight; the ninth is left out, and a reviewer who wants every member of an exported union nameable may add it: 27 names, 489.) With Decisions 1–3 the root gains 4 + 14 + 8 = **26 names, from 462 to 488** (provided nothing else is added between now and the PR).
4. **Add an export-surface contract test** to `test/public-surface.test.ts`, derived and not retyped (the file's own doctrine): generalise `reachableNamedTypes` to accept a function or variable declaration and walk only its type parameters, parameters and return type (never the body), start from the four values above, stop expanding at names the root already exports, and require every name reached to be exported. The eight C2 names belong to no signature closure, so the test asserts them from a short named list (or derives them from the members of `ResolvedElement` with the same walker, if the ninth name is added). Also assert that the four values exist on the root namespace. A second, behavioural case: for `examples/imports.arch` and `examples/museum-wings.arch`, `resolvePlan(source, { world })` yields as many `ir.elements` as `describe()` sees (guards against falling back to the unlinked path).
5. **Declare the stability level below in JSDoc at each declaration** (`resolvePlan`, `joinWallSet`, `doorSwing`, `loopsToPolygons`) and in a CHANGELOG `[Unreleased]` → `### Added` entry stating "output byte-identical".
6. **Add no field to any IR type, no argument to any function, no diagnostic code.** If the 3D package later needs a new fact, it is a separate additive change with its own justification (plan §2.8 item 11 is the one anticipated case: an optional ownership priority, only if a real mixed-height plan appears).

## Stability level

**Recommendation: public and append-only, with a deliberately narrow commitment — not labelled experimental.** The core maintainers decide; the evidence is:

| Evidence (`main@1a1efd9`) | Reading |
|---|---|
| `resolvePlan` is called from **12 modules under `src/`** (`analyze`, `describe`, `lint`, `finish`, `furnish`, `repair`, `suggest`, `plan-json`, `lsp`, `while-fix`, `cli/commands-analyze`, `cli/commands-author`), from **32 test files (75 call sites)** and from `scripts/probe-rooms-tiling.ts`. Its JSDoc says it runs the same parse → link → resolve pipeline as `compile`; `docs/agents/architecture.md` describes `analyze.ts` as the "shared resolve" plus the circulation/occupancy grids | It is already the load-bearing internal contract. Changing its shape is expensive today whether or not it is exported |
| `planToJson` (public, schema-pinned) is built on it, as are `describe()` and `lint()` | Its results are observable through three public functions, so its *behaviour* is already pinned by those functions' tests |
| JSDoc states the semantics: never throws on user-source problems; `ir` is the **lowest** storey (page 1) or `null` on fatal errors; `diagnostics` aggregates **every** storey (each tagged `Diagnostic.level`); `levels` is an *append-only* field, `[]` for a single-storey plan. Measured: `ResolvedLevel = { level, name?, ir, diagnostics }`; `townhouse` gives levels `1:Ground floor`, `2:First floor`, `3:Second floor`; `one-room` gives `levels = []` and `ir.level` undefined; `hillside-villa` (levels **and** `place`) resolves 2 levels | The semantics are documented in the source and match the measurement; "each level carries its own `ir`" answers the part of plan appendix H item 31 that asked it |
| `packages/mcp` imports only the package root (`@chanmeng666/archlang`) and feature-detects newer exports through a namespace import (`Partial<Pick<typeof coreNamespace, …>>`); no workspace package uses `resolvePlan` | There is **no external consumer** today. The commitment is new; this is the cost the owner accepted under Q18 |
| `CHANGELOG.md` states the project "adheres to Semantic Versioning"; [ADR 0018](../../adr/0018-zero-dep-wall-joinery.md) records that "`src/index.ts` is append-only" and keeps every `GeometryBackend` export "documented deprecated" instead of deleting it; `src/types.ts` carries one `@deprecated` ("removed in 2.0", ADR 0021) | The existing practice is: exports are append-only; removal goes through deprecation and a major version |
| No `@experimental`, `@beta` or `@alpha` tag appears under `src/`, `docs/agents/` or `docs/adr/`; `@internal` appears in three files (`reroll.ts`, `analyze/circulation.ts`, `describe.ts`) and each time means "exported from its module for a test or a signature, not public API, not re-exported by `src/index.ts`" | The convention has exactly two tiers — public (in `src/index.ts`) and `@internal` (not). Inventing `@experimental` for three functions would be a new convention |
| `package.json` has no `"./analyze"` subpath, only `"."` and `"./link"` | The root is the only surface a downstream package can name; the release gate `packages/mcp/scripts/check-core-exports.ts` checks **subpaths** only, so it needs no change [read from the script; not run] |

**What the level commits the core to** (the narrow part): (a) the signature `resolvePlan(source: string, opts?: AnalyzeOptions): { ir: ResolvedPlan | null; diagnostics: Diagnostic[]; levels: ResolvedLevel[] }`, with fields only ever *added*; (b) the semantics quoted above (never throws on user-source problems; lowest storey in `ir`; all storeys' diagnostics aggregated; `levels` empty for one storey); (c) `joinWallSet(walls, groupKeys, split?)` returning `JoinedWallSet | null` and `doorSwing(door)` returning `DoorSwing | null`, with the shapes in the 14 types; (d) the closure types stay nameable from the root. **What it does not commit to:** underscore-prefixed fields on IR types (`_swingBuilding`, `_mirror`, `_tail` …; the downstream package must not read them), the *order* of `diagnostics` beyond what the tests pin, the numeric tolerances inside the joinery (e.g. `ARC_STEP_DEG = 7.5` in `src/geometry/arc.ts`) — the 3D package pins its own discretisation and records the core version in its output — and `parse`/`link`, which stay private.

**Why not the alternatives:** *Experimental* would signal "may change in a minor", which the 3D package cannot build on and which has no precedent here. *Unexported with deep imports* (the 0030 reversal condition) keeps the cost invisible and breaks on extraction. *Stable with the full `ResolvedPlan` closure* would commit the core to 27 more names (see Alternatives). The proposed middle path costs the core one test, one JSDoc block per function and the habit of treating a signature change as a minor/major event — which for a function with twelve internal callers it nearly is already.

## Downstream contract

The consumer is `@chanmeng666/archlang-3d` (incubated in `packages/archlang-3d`; it must not import `src/*`).

1. **Surface snapshot test (downstream).** `packages/archlang-3d/test/core-surface.test.ts` (light, runs in the core's `npm test`): assert that each required value exists on `await import("@chanmeng666/archlang")`, and — with the TypeScript compiler API, same technique as the core test — that each required type name is exported from `index.d.ts`. The list is the 26 names of Decisions 1–3, kept in one constant. A core change that removes or renames one turns the downstream test red *before* the core's own release.
2. **Semver handling.** Adding an export is a minor. Changing a committed signature or semantic (Stability level, items a–d) is a major. Removing an export is a deprecation first (`@deprecated` in JSDoc plus a CHANGELOG "Deprecated" line) and a removal only in a major — the ADR 0018 / `GeometryBackend` precedent. The downstream package pins `peerDependencies` to the first core minor that carries the exports; the number is unknown until the core releases (the plan's `^1.44` is an assumption; plan §2.8 item 4).
3. **Version skew.** The package's CI runs against the latest *published* core and against `main` (the published 1.43.1 already cannot parse three examples that `main` can). On start-up the adapter feature-detects (`typeof resolvePlan === "function"`) and fails with a specific diagnostic naming the missing export and the minimum core version, rather than a `TypeError`. While the core PR is not merged, the prototype branch may import `../../src/analyze.js` relatively, recorded as technical debt R1; nothing on `main` of the 3D package may depend on that.
4. **No reading of private fields.** Only fields documented on the exported IR types are consumed; underscore fields are off limits (plan §2.3). A lint rule or a test greps the package's sources for them.
5. **Deprecation signal.** If the core ever wants to retire one of these exports, the CHANGELOG line and the JSDoc are the signal the 3D package's contract test and release notes read; the core is not asked to coordinate beyond that.

## Consequences

- **Positive.** The 3D package consumes the same resolve, joinery and door-leaf code the plan drawing uses, so a drawing and its model cannot disagree for want of a second implementation (ADR 0018's argument, applied downstream). The `public-surface` guard grows from one root (`SceneSummary`) to the signatures that matter to the one known downstream consumer. The core's byte-identity laws are untouched: no output path changes.
- **Cost on the core.** 26 new public names; one JSDoc block each for four functions; the test generalisation (≈ 30–50 lines, estimate); an API surface that now needs a deprecation cycle to change. `joinWallSet` is also called by the axonometric view that ADR 0021 schedules for removal (backlog V.5, 2.0); exporting it does not interact with that removal because the plan path still uses it.
- **Risk: exporting a function exposes today's IR vocabulary.** The full closure of `resolvePlan` reaches 40 own names the root does not export (see Alternatives); 13 of them are exported by this ADR (`AnalyzeOptions`, `Arc`, `DoorHinge`, `DoorSwingDir`, `Opening` and the eight C2 names), **27 remain**. The proposal does not widen that debt and does not repair it; whether the 3D adapter needs more of them than the eight C2 names is verified in the plan's M0 D2 (appendix H item 38).
- **Risk: `levels` semantics drift** (e.g. nested `place` inside levels). Mitigated by the behavioural test above and by the downstream contract test.
- **Backlog.** P3-2 (IFC4 export) is re-scoped when 3D work starts: the IR fields it needs already exist and are consumed through the exports above; no new field is added here (plan §2.7, "与 P3-2 协调").

## Alternatives considered

- **Do not export; deep-import from the monorepo.** Zero core change, rejected as the steady state: bypasses the published surface, breaks on extraction, and the cost of every later refactor of `analyze.ts`/`wall-lowering.ts` becomes invisible. Kept as the temporary prototype route only (R1).
- **Export `parse` and `link` instead of `resolvePlan`.** Finer-grained but widens the contract: `link`'s options and diagnostics would have to stay stable too. Rejected (plan `research/01` A2).
- **Plan JSON only.** Rejected on the spike's evidence: 13 of 32 compilable examples (41 %) need information Plan JSON does not carry; arcs flatten to chords; derived walls are absent. PS3.9 (PR #232) lets a component that derives its walls travel in Plan JSON, but still as the `walls from rooms` statement, never as walls (measured: a two-unit synthetic plan has 7 walls in the IR, 6 derived, and 1 wall in Plan JSON), so the conclusion stands.
- **Export the full transitive closure of `resolvePlan`.** Applying the existing test method literally to `resolvePlan` reaches 139 own types, 40 of them unexported — including `RStair`, `RRoof`, `RVoid`, `FurnitureAuthored`, `WallRelation`, `OpeningRelation`, `DatumTable`, and parser internals such as `Token`, `TokenType`, `Expr`, `BinOp`, `Value`, `Env`, `ParseExprOpts`. Most arrive through the already-exported `ResolvedPlan`/`CompileOptions`, i.e. they are a **pre-existing** hole, not a consequence of this ADR. Rejected for this change: it would publish the expression parser's internals to cover a gap that is not ours to widen here. The frontier closure (stop at exported names) is the scope; the 40 are listed in `spike/results/export_closure_refs_1a1efd9.json` for a separate decision.
- **A new tier (`@experimental`).** Rejected under Stability level.
- **Subpath export `@chanmeng666/archlang/analyze`.** Would keep the root small and make the commitment explicit, but adds a subpath the mcp release gate and `exports` map must carry, and splits the surface in two. Not recommended; reasonable if the maintainers prefer not to widen the root.
