# 2026-11 促销额度测试计划：结论、教训与开发方向

2026-11-15 至 11-16，所有者批准用 $200 的 Claude 促销额度（与 ≤ $30 的 OpenAI 额度）做一轮 ArchLang 测试（P0–P5 与一次 T3）。本文把这一轮**能落档的结论**收在一处，供以后排期参考。

**边界（先读）：**

- **数字的出处。**
  - 第 2 节的数字都来自已合并的带日期记录（各小节注明出处）。本文只做汇总与解读，不发布新的测量；与记录冲突时，以记录为准。
  - 第 5、6 节的计数与费用来自这一轮的运行日志、各次运行的自报和 Console 余额读数。它们不在任何记录里，只作参考。
- **T3。** 唯一的结论是 `eval/live-runs/2026-11-t3-result.md` 的原文（第 2.4 节原样引用）。本文不对 loop 增益作任何一方向的声明（铁律）。
- **跨提示词或裁判版本的比率不可比。** 每一对"之前/之后"同时改了编译器和作者提示词（`spec.llm.md`），差异分不开。本文凡是这样的比较，都只是对观察差异的描述，不是因果估计，也不声明显著性。
- **L1 不是 loop。** L1 是对一次写成的回复确定性地跑 `arch fix` 与 `arch repair`（只用 machine-applicable 一级，`eval/l1.ts`），不再调用模型。它的差值属于工具层，不是模型 loop 的增益。
- **保真评测单独看待。** `eval:fidelity-live` 只单独报告，不与任何其他评测比较（RM-D46）。
- **第 4 节是建议，不是裁定。** 是协调者的排期建议，进不进排期由所有者定；第 7 节的卡已写进 `docs/backlog.md`，状态是 `todo`。

## 2. 测量结论

### 2.1 可写性：CO-1、CO-2 前后，valid 上升的模型多，intent 只有 gpt-5.5 与 Fable 有变化

均为 3 次运行之和，n = 78；数据见 remeasure 记录。

| 模型 | valid：CO-1 前 → CO-1 + CO-2 后 | intent：前 → 后 | L1 intent（后） |
| --- | --- | --- | --- |
| Haiku 5.5 | 45 → 51 | 23 → 22 | 40 |
| Sonnet 5.5 | 53 → 74 | 47 → 46 | 63 |
| Opus 5.5 | 68 → 69 | 48 → 48 | 59 |
| Fable 5.2 | 67/76 → 77 | 61/76 → 68 | 68 |
| gpt-5.5 | 34 → 62 | 15 → 26 | 43 |

**观察到的（不是因果估计）：**

- **valid：** Sonnet 与 gpt-5.5 的前后区间不重叠，其余模型的区间重叠。Opus 只从 68 到 69。
- **报错类别：** 与 CO-1、CO-2 针对的写法有关的报错几乎消失。
  - 顺序类报错从几十条降到个位数。
  - gpt-5.5 的 ``needs a `size` `` 报错：CO-1 前 70 条，CO-1 后 111 条，CO-1 + CO-2 后 0 条。
  - 报错类别的变化与"接受模型自然写法"的方向一致，可作为继续这条路的理由。但每对之间提示词也变了，这个数据不能把功劳单独记给语法改动。
- **intent：** 只有 gpt-5.5（15 → 26）和 Fable（61/76 → 68/78）有变化，Haiku、Sonnet、Opus 基本不变。
- **L0 → L1 差值（工具层）：** Sonnet 46 → 63，Haiku 22 → 40，gpt-5.5 26 → 43，Fable 68 → 68。
- **模型之间：**
  - Fable 5.2 在 CO-1 + CO-2 后的 valid（77/78）与 intent（68/78）都最高。
  - 那一组里 Haiku 的 intent 最低（22/78）。前两组里 gpt-5.5 更低（15、16）。

### 2.2 gpt-5.5 的 intent 失分：门洞被挡与开口放置被拒

EV.1 只针对 gpt-5.5，对照的是 2026-07-11 那次运行；07-12 基线运行的逐 brief 结果已不存在。七月能达到 intent 的 brief，在新运行里丢掉了 26 次：

- **19 次是物理 lint，每一次都有 `W_DOORWAY_BLOCKED`。** 这条规则在 10-26 起也检查无门扇的开口，并从墙面量每个接近方向（`c2978a47`）。EV.1 无法区分这 19 次是规则变严、编译几何变了、提示词还是模型造成的。
- **7 次是编译报错。**
  - 其中 6 次是七月之后才有的开口放置拒绝（C-jamb、C-ext、C-par，`38bff76f`，ADR 0028 § 5）。
  - 第 7 次是 `Unknown statement`，写的是 `offset`，原因未归属。
- **没有一次是房间数、标签或面积这类断言失败。**

逐 brief 的计数与一个统一的约三分之一的比率一致，所以单个 brief 的得失不携带信号。

**含义（只对 gpt-5.5）：** 在这些运行里，模型栽在**家具与门洞**和**开口离墙角太近**这两种几何细节上，而不是房间关系上。Claude 模型的 intent 失分没有逐 brief 的统计，这里不推广到它们。

### 2.3 约束保真：四个模型都没有"洗约束"

P3 记录（每个模型 30 次，在 CO-1 之前的 `ab37b3ef`）：

- **不可满足的 brief：** 四个模型在 15/15 次里都声明了不可满足，并准确指出冲突的约束。
- **洗约束：** 悄悄改掉给定数字的情况为 0/30。
- **失分：** 全部是可满足的 brief 编译不过，Sonnet 6 次，Haiku 2 次。

**含义：** 在那时的提示词下，"不可满足就明说"这条行为是稳的，应当保留。记录写明，每个模型 30 次不足以区分任何两个模型。这组运行之后没有重跑；按 RM-D46，它不与本文其他任何评测比较。

## 3. 测量方法的教训

1. **基线必须和当前提示词、当前检查同时成立。**
   - 七月基线量完之后，作者提示词 241 行里改了 146 行，lint 和编译检查也变了，可是没有任何东西提醒"基线已经过时"。
   - EV.1 花了一整轮才确认两边不可比。
   - 对策：基线记下提示词与语料的哈希，提示词变了，"Delta vs baseline"就要显式标出（卡 EV.3）。
2. **不存方案源码，就分不清原因。**
   - EV.1 回答不了"是模型写法变了、规则变严了，还是编译器多画了家具"，因为两边都没有留下每个 brief 的源码。
   - 对策：live 运行把每个 brief 的方案源码存下来（卡 EV.2）。RM-D53 裁定可以放进公开的 artifact，原始回复不发布。
3. **单次运行不能当基线。**
   - 同一提交上的三次 gpt-5.5 运行，在 26 个 brief 里有 15 个结果互相不一致。
   - RM-D52 取三次中 valid 与 intent 居中的那次。逐项中位数是 22/9/0，那次的 sound 与 L1 都是三次里最高的，这已在基线 `note` 里写明。以后应同样取三次运行并写明取法。
4. **固定提交跑测量。**
   - P1 有一组跑到一半，主 checkout 被别的会话快进了一次（provenance 里有记录）。
   - 之后都在独立的 detached worktree 里跑，提交不会在中途移动。今后照此办理。
5. **对照组尽量用同一提交。**
   - P1 与 P2 的"最后一组"在不同提交（`68064111` 与 `2a210589`）。两者之间有约 30 个提交，其中只有一个（ST.2）改了 `src/`。
   - 记录写明了这一点，并说明语料里没有楼梯 brief。

## 4. 开发方向（建议，按收益排序）

1. **家具与门洞（gpt-5.5 intent 的最大失分）。**
   - 先评估 `W_DOORWAY_BLOCKED` 对"只擦到门扇摆动区"的家具是否过严（RR.8 第 2 项）。
   - 再看 `finish` 或 `repair` 能否把挡门的家具挪开。
   - 两件都会动 lint 或修复，需要按铁律做逐字节对照与语料复测。
2. **开口放置被拒时给出挪动修复（卡 EV.5，先设计）。**
   - C-jamb、C-par 现在只是拒绝。给出"挪到最近的合法位置"能帮作者。
   - 但 L1 只应用 machine-applicable 一级：只有能证明正确的挪动（ADR 0011 的标准）才会改变 L1 的数字，`maybe-incorrect` 一级的修复不会。设计要在 ADR 0005 与 ADR 0028 § 5 之内做。
3. **继续接受模型的自然写法。**
   - CO-1、CO-2 之后剩下的顺序类报错，是把 `offset`（Haiku 5 次，gpt-5.5 也有）和 `hinged`（Haiku 2 次）当成语句来写。
   - 先给针对性的解析提示，像 U.6 给 `uses balcony` 的提示那样（卡 EV.4）。值不值得变成语法，看提示上线后的数据再说。
4. **测量基础设施（第 3 节）。**
   - EV.2 存每个 brief 的方案源码，EV.3 记提示词哈希。
   - 这两件做完，下一次所有者批准的复测才能把原因分开。
5. **工具层对小模型的作用。**
   - Haiku 的 L0 intent 在 CO-1 + CO-2 那一组最低，而对它一次写成的输出跑 `arch fix` + `arch repair`（工具层）后是 40/78（2.1）。
   - 面向小模型的文档与 MCP 提示，可以更明确地建议在输出后跑这两个工具。这只是工具层的使用建议，不涉及模型 loop。

## 5. 代理开发流程的借鉴（P5）

本节的计数来自这一轮的审查记录与 PR 线程，不在任何带日期的记录里。

- **无头执行者便宜，审查不能省。**
  - `claude -p` 加 Opus 5.5 做一张卡，按各次运行的自报约 $0.4–1.4。
  - 多数 PR 在两轮审查里都有必须修的问题，例如：
    - 平局判定在浮点下失效（#822，第一轮）；
    - 选中房间后卡片立刻关闭（#824）；
    - 功能 PR 手动改了版本号，把插件指向一个还没发布的 shim（#815）；
    - 解析树摘要被改动（#848，第一轮）；
    - 修复建议在循环里无上限地重复生成，且不计入步数预算（#848，第二轮）；
    - 报告里的数字和 artifact 对不上（#837）。
  - PR 描述里也有说过头的地方，例如 #841 说"输出字节不变"，而部署后的页面日期会变。这一条第一轮判为可合并，事后在 PR 上更正。
  - 结论：**两轮新鲜上下文审查加 CI，是这套做法能成立的前提。**
- **本地门禁看不到的 CI 守卫最常让执行者误报"已通过"。**
  - 例子：`opaque-literal-guard`、`docs-flags`、`lint-fix-texts`。这些文本守卫不在 `check:quick` 选中的就近测试里。
  - 对策：改动触及错误目录或文档时，让 `check:quick` 也跑这几项（卡 AG.1）。
- **规则写进仓库才不会重犯。**
  - 版本号只由发版 PR 的 `release:pin` 改，这一条已写进 `.claude/rules/mcp.md` 与 `new-mcp-tool.md`。
  - backlog 结卡的格式应在执行者简报里逐字给出，这一轮多次写错。
- **合并列车省时省 CI。**
  - 同批 PR 共同改动的往往只有生成的 `docs/backlog-index.md`，由列车的 `gen:all` 统一重新生成即可。
  - 冲突的 PR 不会触发 CI，需要先 `sync:main`。
- **审查轮数上限用完后，剩余问题写成卡（RR.1–RR.8）。**
  - 不开第三轮；协调者亲手修掉的阻塞问题，以 CI 全绿为合并依据，并在 PR 上写明。

## 8. P6：用余下的额度做卡（2026-11-16）

所有者在余额 $55.30 时要求继续用。做了 12 张卡（RR.1、RR.3–RR.7、EV.3、EV.4、AG.1、WS.4、N.4、M.21），全部合并（`handoff.md` 有 PR 与列车号）；EV.2 与 EV.5 没有做（EV.2 要改 live 工作流，EV.5 先要设计）。

- **审查仍是主要的价值来源。** 第一轮审查过的 11 个 PR 里，5 个记了 major 或 blocker（#855、#864、#865、#866、#868），另 3 个（#861、#867、#872）有实质的修复轮，多数是测试钉的是错的东西（标题说的比断言多）、措辞超出证据、文本守卫的触发面太宽，没有一个是看测试绿就能发现的。

- **审查者的“改完再看”可以由协调者自己做**：措辞、卡片、注释这类修复由协调者直接改，比再派一轮无头执行便宜；代码修复仍派执行者，再给新上下文的第二轮审查。

## 9. P7：余下的额度（2026-11-17）

余额 $34.28 时所有者要求用完。一个排队运行器按顺序跑卡和修复轮，每次开跑前汇总已花的钱，已花加下一项上限超过停止线就不开；停止线先定 $31.5、后放到 $32.3，保证最坏情况也碰不到所有者购买的额度。12 张卡加修复轮共约 $30.1，读数 $4.14 时所有者叫停，剩下的改用订阅额度。
