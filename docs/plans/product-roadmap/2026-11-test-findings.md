## 2. 测量结论

### 2.1 可写性：CO-1、CO-2 之后，"写得出能编译的方案"明显变好，"写对意图"没有跟着变好

均为 3 次运行之和，n = 78；数据见 remeasure 记录。

| 模型 | valid：CO-1 前 → CO-1 + CO-2 后 | intent：前 → 后 | L1 intent（后） |
| --- | --- | --- | --- |
| Haiku 5.5 | 45 → 51 | 23 → 22 | 40 |
| Sonnet 5.5 | 53 → 74 | 47 → 46 | 63 |
| Opus 5.5 | 68 → 69 | 48 → 48 | 59 |
| Fable 5.2 | 67/76 → 77 | 61/76 → 68 | 68 |
| gpt-5.5 | 34 → 62 | 15 → 26 | 43 |

**含义：**

- **被模型自然写法撞上的报错几乎清零。** 前后差的是语法糖（CO-1：子句任意顺序、类别后可写 `id=`；CO-2：任何放置方式都可以省略 `size`）。顺序类报错从几十条降到个位数，gpt-5.5 的 ``needs a `size` `` 报错从 111 条降到 0 条，它的 valid 也从 34 升到 62。
  - 方向：**"模型自然会写、意思又不含糊的写法，就接受"是 valid 上最便宜的杠杆。**
- **intent 基本没动。** 现在的瓶颈不是语法，而是写出来的方案过不了意图检查，主要是物理 lint（见 2.2）。
- **L1 覆盖层把 intent 拉高不少。** 它是确定性的 `arch fix` + `arch repair`，不额外调 API；Sonnet 46 → 63，Haiku 22 → 40，gpt-5.5 26 → 43。Fable 本来就高，68 → 68 没有变化。这是记录里的 L0 → L1 差值，不是 loop 增益声明。
- **模型之间的差距大于语言改动带来的差距。** Fable 5.2 在 valid（77/78）与 intent（68/78）上都最高；Haiku 的 intent 最低，三组都在 22–24/78。

### 2.2 intent 的主要失分来源：门洞被挡与开口放置的拒绝

EV.1 对 gpt-5.5 做了逐 brief 诊断：七月能达到 intent 的 brief，在新运行里丢掉了 26 次，原因如下。

- **19 次是物理 lint，每一次都有 `W_DOORWAY_BLOCKED`。**
  - 这条规则 10-26 起也检查无门扇的开口，并从墙面量每个接近方向（`c2978a47`）。
  - CO-2 之后，没写尺寸的家具也会按目录尺寸画出来，于是更多家具会落进门洞。
- **7 次是编译报错，其中 6 次是开口放置被拒。**
  - 三类拒绝：门窗离相交墙太近，开口被拒而不是被挪开（C-jamb）；窗开在内墙上（C-ext）；边与共享边平行、无法量偏移（C-par）。
  - 这几条报错都是 10-21 才有的（`38bff76f`，ADR 0028 § 5）。
- **没有一次是房间数、标签或面积这类断言失败。**

**含义：** 模型通常把房间关系写对了，栽在**家具挡门**和**开口离墙角太近**这两种几何细节上。这是今后提高 intent 最直接的两个方向（第 4 节第 1、2 条）。

### 2.3 约束保真：四个模型都没有"洗约束"

P3 中，每个模型 30 次，其中 15 次是不可满足的 brief。四个模型在 15/15 次里都声明了不可满足，并准确指出冲突的约束；洗约束（悄悄改掉给定数字）为 0/30。

失分全部出在可满足的 brief 上，原因是方案编译不过：Sonnet 有 6 次，Haiku 有 2 次。

**含义：** "不可满足就明说"这条行为在当前提示词下是稳的，应当保留。编译失败仍是 Sonnet 的短板，与 2.1 中它 CO-1 前 valid 偏低是一致的。

**注意：** 这组运行在 CO-1 之前，事后没有重跑；而且它与其他任何评测都不可比较（RM-D46）。

### 2.4 T3

结论只按记录原文：在本语料与本协议下，两个模型都**没有检测到** loop 与等预算重采样的差异。原文同时写明，在这个分辨率下"未检测到"不是"没有效果"的证据。

T3 已经用完，不再重跑（铁律）。

## 3. 测量方法的教训

1. **基线必须和当前提示词、当前检查同时成立。**
   - 七月基线量完之后，作者提示词 241 行里改了 146 行，lint 和编译检查也变了，可是没有任何东西提醒"基线已经过时"。
   - EV.1 花了一整轮才确认两边不可比。
   - 对策：基线记下提示词与语料的哈希，提示词变了，"Delta vs baseline"就要显式标出（卡 EV.3）。
2. **不存方案源码，就分不清原因。**
   - EV.1 回答不了"是模型写法变了、规则变严了，还是编译器多画了家具"，因为两边都没有留下每个 brief 的源码。
   - 对策：live 运行把每个 brief 的方案源码存进 artifact（卡 EV.2）。原始回复仍然不发布。
3. **单次运行不能当基线。**
   - 同一提交上的三次 gpt-5.5 运行，在 26 个 brief 里有 15 个结果互相不一致。
   - 基线从 RM-D52 起取三次中位数，以后也应如此。
4. **固定提交跑测量。**
   - P1 有一组跑到一半，主 checkout 被别的会话快进了一次（provenance 里有记录）。
   - 之后都在独立的 detached worktree 里跑，提交不会在中途移动。今后照此办理。
5. **记录要写清每组的提交。**
   - P1 与 P2 的"最后一组"实际是不同提交（`68064111` 与 `2a210589`），差了 ST.2 这一个提交。
   - 记录写明了这一点，并说明语料里没有楼梯 brief，因而可以接受。以后应尽量让对照组用同一提交。

## 4. 开发方向（建议，按收益排序）

1. **家具与门洞（intent 的最大失分）。**
   - 先评估 `W_DOORWAY_BLOCKED` 对"只擦到门扇摆动区"的家具是否过严（RR.8 第 2 项）。
   - 再看 `finish` 或 `repair` 能否把挡门的家具挪开，或在报错里给出一个可机器应用的挪动修复。
   - 两件都会动 lint 或 L1，需要按铁律做逐字节对照与语料复测。
2. **开口放置被拒时给出修复（valid 与 intent 的第二来源）。**
   - C-jamb、C-par 现在只是拒绝。如果能给出"挪到最近的合法位置"这样的修复，至少是 `maybe-incorrect` 级，L1 就能接住这类失败（卡 EV.5，先设计）。
3. **继续接受模型的自然写法。**
   - CO-1、CO-2 之后剩下的高频报错，是把 `offset`（Haiku 5 次，gpt-5.5 也有）和 `hinged`（Haiku 2 次）当成语句来写。
   - 先给针对性的解析提示，像 U.6 给 `uses balcony` 的提示那样（卡 EV.4）。值不值得变成语法，看提示上线后的数据再说。
4. **测量基础设施（第 3 节）。**
   - EV.2 存每个 brief 的方案源码，EV.3 记提示词哈希。
   - 这两件做完，下一次所有者批准的复测才能把原因分开。
5. **Haiku 档模型。**
   - 它的 intent 在三组里都是最低，L1 却能把它从 22 拉到 40（2.1）。
   - 面向小模型的用法（MCP、技能）应当默认走 compile → fix → repair 的闭环，而不是一次写成；文档与 MCP 的提示可以更明确地这样引导。这只是文档方向，不是 loop 增益的声明。

## 5. 代理开发流程的借鉴（P5，约 20 个 PR）

- **无头执行者便宜，审查不能省。**
  - `claude -p` 加 Opus 5.5 做一张卡，按各次运行自己的报告约 $0.4–1.4。
  - 但大约一半的 PR 在第一轮审查里有阻塞或必须修的问题，例如：
    - 平局判定在浮点下失效（#822）；
    - 选中房间后卡片立刻关闭（#824）；
    - 功能 PR 手动改了版本号，把插件指向一个还没发布的 shim（#815）；
    - 解析树摘要被改动（#848）；
    - 修复建议在循环里无上限地重复生成，且不计入步数预算（#848）；
    - PR 描述写"输出字节不变"而事实不是（#841）；
    - 报告里的数字和 artifact 对不上（#837）。
  - 结论：**两轮新鲜上下文审查加 CI，是这套做法能成立的前提。**
- **本地门禁看不到的 CI 守卫最常让执行者误报"已通过"。**
  - 例子：`opaque-literal-guard`、`docs-flags`、`lint-fix-texts`。这些文本守卫不在 `check:quick` 选中的就近测试里。
  - 对策：改动触及错误目录或文档时，让 `check:quick` 也跑这几项轻量守卫（卡 AG.1）。
- **规则写进仓库才不会重犯。**
  - 版本号只由发版 PR 的 `release:pin` 改，这一条已写进 `.claude/rules/mcp.md` 与 `new-mcp-tool.md`。
  - backlog 结卡的格式也应在执行者简报里逐字给出，这一轮多次写错。
- **合并列车省时省 CI。**
  - 同批 PR 共同改动的只有生成的 `docs/backlog-index.md`。由列车的 `gen:all` 统一重新生成，比逐个同步 main 省事得多。
  - 冲突的 PR 不会触发 CI，需要先 `sync:main`。
- **审查轮数上限用完后，剩余问题写成卡（RR.1–RR.8）。**
  - 不开第三轮；协调者亲手修掉的阻塞问题，以 CI 全绿为合并依据，并在 PR 上写明。
