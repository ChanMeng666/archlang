## 0. 一页结论

两场调研从不同方向得出同一个结论。

**用户要的，不是"一个会画平面图的 AI"**。那个已经有人免费或很便宜地给了。用户要的是三样：

- **信得过的平面**：尺寸、房间清单、锁定的数值不漂移；
- **改得动**：改一处不动全局；
- **交得出去**：能交给下一步，CAD、立面、剖面。

growth 的合成用三类彼此独立的来源交叉核对这一点：第三方的原话、下游应用的 brief 与行为、公开讨论与研究。论坛材料又从业内人和业主两边独立印证了一次。

**ArchLang 的结构正好对着这个需求**：纯文本、确定、诊断落在字节位置。但它最核心的承诺"检查"，今天在首次接触的平面上只报出 57 个缺陷里的 8 个（`handoff.md` §6，RM1.1a）。

语言调研也指向同一个瓶颈：剩下的失败是语义问题，不是语法问题。实测编译通过 13–22/26，lint 全过只有 0–6/26，剩下的编译错误多是开口被拒（`../ai-first-language/README.md` §1、§5）。

2026-11-18 的硬 brief 试用还找到四个"说错数字"的缺陷：

- 恰好 40.000 m² 的平面报成 40.01 m²；
- 两层的房子，标题里的总数只算入口层；
- 12ft + 12ft 不等于 24ft；
- 不可能满足的 brief 没有一条诊断说"不可能"。

前两个我在 1.63.0 上复现过（§1.3）。它们直接打在 v2 规定"只有三样可以说是测量过的"里的"精确面积"上。

**所以 v3 的顺序是：**

1. 先让数字说对，让代理读得懂语言（阶段 1）；
2. 再把检查的覆盖率当成第一投入（阶段 2）；
3. 然后让编辑变成一句话（阶段 3）；
4. 最后是不止一张平面图、交得出去（阶段 4）。

新元素、新渠道、新视觉都排在这些后面。

### 1.3 2026-11-18 硬 brief 试用（growth `research/2026-11-18-hands-on-trials-pascal-drafted-hard-briefs/`）

五份硬 brief（两层带楼梯、整图缩小一成、英尺英寸、不可能的 brief、L 形房间）分别交给 ArchLang 1.63.0、Pascal Editor 1.1.5 和 Drafted 免费档。

**对 ArchLang 有利的：**

- 能按 brief 设门槛（`validate --intent`）；另外两家都查不了 brief。
- 默认出带尺寸的图纸。
- `impact` 把整图缩小的 26 处变化逐条解释了原因。
- SVG、DXF、PDF、PNG 全部免费导出。

**ArchLang 的缺陷**（前两条我在 1.63.0 上复现过，命令是试用证据里 `h4.arch`、`h1.arch` 的 `arch describe`）：

1. **总面积是用四舍五入后的房间面积相加的。** 各房间的精确面积 6.675 + 6.65 + 6.675 + 13.75 + 6.25 = 40.000 m²，但报出的是 40.01 m²；`validate --intent` 据此判 "total 40.01 m² outside [0, 40]"，是一次误判。（复现）
2. **两层平面的标题只算入口层**：`describe` 第一行是"4 room(s), 80 m²"。`--json` 里另有 `gross_internal_area_all_levels_m2`，但标题、caption 和 `<desc>` 用的都是入口层。下游应用曾因此把入口层的数当作整栋总数显示给用户，现在只好自己求和（ArchCanvas 请求清单第 4 条）。（复现）
3. **英尺字面量各自舍入到整毫米**：12ft + 12ft = 7,316，不等于 24ft = 7,315。一处 1 mm 的重叠引出 19 条错误，根因 `E_ROOMS_OVERLAP` 排在最后；消息里还出现 `3657.6000000000004` 这样的浮点噪声；输出只有 mm 和 m²。
4. **不可能的 brief 只报"没满足"，不报"不可能"。** 评测代码里已经有 `proveInfeasible`（`eval/fidelity.ts:363`），CLI 没有用它。
5. **整图缩放只能手改坐标**；朴素的线性缩放报了 14 条错误。Pascal 用一个可撤销的补丁做完了同一件事。
6. **单位和"标称还是净尺寸"不先问**：10 x 8 m 被当成中线尺寸，画出外缘 10,200 x 8,200。Drafted 会先确认。

**竞品：**

- Pascal 的检查面广，但只查几何：楼梯、楼板、可达、墙外的开口。它不查 brief，不查房间数和面积。它的本地文字转平面对两份不同的 brief 返回同一个模板，还判为合法。它的状态是带随机 id 的 JSON 场景。2D 视图里没看到尺寸标注。
- Drafted 免费档 2026-11-10 之后收紧了：不能导出，不能编辑，每周一份 brief。

## 2. 原则（在 v2 原则之上）

1. **数字说对，先于一切新能力。** 一个说错的面积，比少一个功能更伤信任；"精确面积"是三样"可以说测量过"之一。
2. **检查的覆盖率是第一投入。** 每条缺陷类要么加 lint，要么明写"不检查"（RM9.0、RM9.6）；以 RM1.1b 为验收。
3. **每张卡写出它回答哪个 N#。** 回答不了的，往后排。
4. **免费的测量先于付费的测量，测量先于建造**（AF21、AF22、AF26、RM9.0）。
5. **不和 Pascal 拼 3D、BIM 和格式数量。** 做"纯文本 + 检查 + 带尺寸的图纸"这一层；桥接放在触发之后（阶段 5）。
6. **语言里不做文字转平面的生成器。** 生成是代理和 ArchCanvas 的事；语言负责让写出来的东西能被检查、能被解释、能被改。
7. **下游应用是试验台。** 它每一次失败的生成，都是一条语言或引导上的发现；它的请求按 §1.5 排进来，每做完一条，它那边对应的绕行就删掉。
8. **不变的：** 铁律、v2 §4 的"不做"、发布每次都要所有者对那一次的决定、付费评测归所有者。
