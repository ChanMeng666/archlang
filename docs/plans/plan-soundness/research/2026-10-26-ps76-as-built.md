# PS7.6 as built: `lint` and `validate` open with a one-line summary

Dated 2026-10-26 (branch `feat/lint-summary-line-ps76`). The card: three arm-B authors cut `lint --json`
with `head -c` and repaired only what they saw (café 4 of 23 codes, clinic 2 of 4, studio 5 of 6).

## What shipped

- `src/cli/summary.ts`: `diagnosticsSummary(diags)`, a pure function of the diagnostics. `no warnings`;
  `N warning(s): CODE ×k, …`; with errors `E error(s), N warning(s): …`. Errors lead, each severity's
  codes by descending count, then catalogue order (`ERROR_CODES`), then code text; a diagnostic with no
  code is counted as `uncoded`. Nothing is elided.
- `lint --json` and `validate --json` (both through `report`, and `validate --graph/--intent` through
  `reportWithChecks`): `summary` is the FIRST key; every key after it keeps its order and bytes.
- Text report: the same line first on stderr, then a blank line, when there is at least one diagnostic
  and no `--quiet`. A clean plan prints no line (the `✓ ok` line says it, and its stderr stays empty
  but for the coverage note). The line counts the whole set like `ok`; a `--code`/`--severity` display
  filter does not narrow it (its `(display filter: showing n of m)` note already says so).
- CLI-only: nothing in the library, `lint()`, `compile()` or the public surface changed.
- Teaching: one clause in `skills/archlang/SKILL.md` step 7 (read the `summary` first); the generated
  copies follow (`gen:all`). Docs: `docs/analysis.md` § The summary line. Spec text untouched: the CLI
  list line `arch lint  # architectural soundness warnings` cannot take the clause within the card's
  20-unit allowance, so the spec's headroom is unspent.

## Decisions

1. **`validate`'s summary is the diagnostics' line, without `next`.** The brief suggested its first key
   should also say `next`. PS5.3's law (`test/cli-validate-next.test.ts`) pins `next` as purely
   additive: the output minus `next` equals the output without it. A summary naming `next` would break
   that law, and the acceptance wants the summary to be a function of the diagnostics alone. `next` is
   one of the diagnostics' codes in almost every case, and stays the last key.
2. **No `summary` on the library `lint()`.** A derived field on the return value would touch the public
   surface and ADR 0032's `lint()` digests for no reader who cuts output with `head`.
3. **Digest suites that hash `validate --json` stdout.** Two do: the keep weak law K1
   (`keep-byte-identity`, 269 baseline rows) and K3 (`keep-digests`, 23 rows). The new key moves every
   one of those rows. Rather than re-pin, `test/validate-json-run.ts` exports `withoutSummary`, which
   removes exactly the first key (`^{\n  "summary": "…",\n`), and both measurement bodies apply it: the
   old pins hold unchanged, 292 of 292 rows green, no digest value edited. The summary itself is
   covered by `test/lint-summary.test.ts`.
4. **MCP `lint` tool**: not changed (card PS5.3a territory). It can add the same line from its own
   diagnostics.

## Evidence

- Against `origin/main` (built in a second worktree), `lint` and `validate`, with and without `--json`,
  over all 180 files (34 examples, 146 defect-corpus plans): 720 runs, the output with the summary key
  (or line) removed is byte-identical to main's, exit codes included. 0 differ.
- `lint --json` diagnostics equal `lint()` mapped through `diagnosticToJson` for every plan that
  compiles, byte for byte (`test/lint-summary.test.ts`).
- 200-byte cut (what `head -c 200` shows) over the 180 files, both commands: the first key is
  `summary`, and the cut holds the count and the first code. 95 of 180 plans have diagnostics; the whole
  summary fits in the 200 bytes for all 95 (the widest is 4 codes, 112 bytes, `bath-open-side.arch`).
  A plan with many distinct codes (about 27 bytes each) runs past 200 bytes; the cut then still carries
  the count and the leading, most frequent codes, which is the first thing the card asks for.
- `lint --json` of `examples/two-bed.arch` (clean), first 200 bytes: see the PR body.
- Corpus movement: none. `describe()`, `lint()`, `compile()` and the SVG are not touched; every
  `*-digests` / `*-byte-identity` suite, `taste-digests` and `lint-file-provenance` are green with no pin
  changed, and `eval/judge-fixture.json` is untouched.
- Two key-order assertions moved, by design: `test/lint-coverage.test.ts` (two `Object.keys` lists) and
  `test/cli-validate-next.test.ts` (one) now start with `summary`.
