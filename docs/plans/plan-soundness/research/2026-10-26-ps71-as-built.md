# PS7.1 as built: stages as a first-class idea, `validate --stage <s>`

Dated 2026-10-26 (branch `feat/validate-stage-ps71`, from `main@52e7c71f`). The card: decide the
low-frequency things first, because early errors of proportion cascade (ADAI's staged workflow,
`adai-sketchup.md` idea 2; the two-stage norm in `prior-art.md` §1). `validate --stage <s>` runs only
the rules that mean something up to that stage, and the SKILL's loop advances only when a stage is
clean.

## What shipped

- `src/stages.ts` (new, pure): the ladder `AUTHORING_STAGES`; `codeStage` (a lint code by its
  rule, a compile warning by `COMPILE_WARNING_STAGES`, an error by its family); `predicateStage`
  (an intent assertion); `keepStage` (a `keep`, by what it measures); `diagnosticStage` (a broken
  hard keep by its keep); `atStage(stage, diagnostics, nextInput, kindOf)`, the stage's view that
  `validate --stage` reads. All of these are exported from the package.
- `LintRule.stage` (required, like `layer`): every one of the 45 rules declares it. A rule whose
  codes judge different things gives one stage per code (only `per-room`). `LINT_CODE_STAGES` is
  read off the rules, in `src/lint.ts` beside `LINT_CODE_LAYERS`. No `check()` body changed.
- `validate --stage <brief|rooms|walls|openings|fixtures|drafting>`. It shows the errors and the
  findings of stage ≤ s. `ok`, `--strict`, the intent block's `violations`/`ok` and `next` read that
  set. `summary` opens with `stage <s>: ` and ends with
  `(N later-stage finding(s) held back)`. An `at_stage` block `{ stage, held_back, clean }` comes
  before `keeps` and `next`, and a stderr line in text mode says either "fix what it shows before
  advancing" or "advance to --stage <next>". An unknown stage exits 3 with a did-you-mean.
- Without `--stage`, `validate --json` adds one key: `"stage"`, appended last to every diagnostic
  and to every `--intent` violation. `lint --json`, `lint()`, `describe()`, `compile()` and the
  text reports are unchanged.
- Teaching: SKILL step 7's loop is stage-ordered (rooms → walls → openings → fixtures → the full
  `validate --strict`, advancing when `at_stage.clean`, or when every remaining finding is one the
  author accepts and says so; clean is not permanent). `arch-author.md`'s loop got the same sentences. The spec's self-correction paragraph gained one clause, with the stage names derived
  from `AUTHORING_STAGES`. `docs/analysis.md` has a new § Stages. The CLI reference and the context
  bundle (`arch context`) list the flag from the manifest (`gen:all`).

## Decisions (each: reason, reverse-if)

1. **Six stages: `brief`, `rooms`, `walls`, `openings`, `fixtures`, `drafting`. The card's "room
   graph" and "zoning on a grid" collapse into `rooms`.** Reason: in ArchLang a `room` is declared
   with its place and size in one statement (rooms-first, ADR 0028; relational placement), so the
   topology and its placement on the grid are one authoring act. Also, no check reads a room graph
   without geometry: adjacency is read through doors (decision 4). `brief` is kept as the frame
   (`plan`, units, `site`, `level`s, `let`s, `keep`s): only the language's own diagnostics belong
   to it, and no lint code does. *Reverse-if:* ArchLang gains a topology-only form (rooms named
   and joined before they are placed), or a check that reads a room graph without positions. Then
   split `rooms` into `graph` and `zoning`.
2. **A finding's stage is the EARLIEST stage at which its check can be judged, as the check is
   defined: the stage whose elements it needs, present or absent.**
   - `W_NO_ENTRANCE` reports a missing door, so it is `openings`, not `walls`.
   - `W_ROOM_TOO_NARROW` is defined on the clear width between the inner wall faces, so it is
     `walls`.
   - `W_FLOOR_UNASSIGNED` reads a walled face, and a doorless ring of walls cannot leave one, so it
     is `openings`.
   - `W_ROOM_NO_CLEAR_PATH` is a room packed by furniture, so it is `fixtures`.
   - `W_SWING_OBSTRUCTED` needs only doors: another door's swing is enough. So it is `openings`.

   **A later stage can still add or re-raise an earlier stage's finding.** Walls take the clear
   width a room's size was drawn to (`W_ROOM_TOO_NARROW`, or `W_ROOM_TOO_SMALL` under a
   net-measuring profile, at `--stage walls`). A bed makes a bedroom a double for the
   double-bedroom floors. Furniture pinches `W_PATH_TOO_NARROW` (`tiny-house`). So "clean at stage
   s" is not permanent: each later stage's view shows every earlier stage's codes again, and the
   SKILL, `arch-author.md` and `docs/analysis.md` say so. An author advances when the stage is
   clean, or when every remaining finding is one they accept and say so.

   Reason: a stage is clean when nothing judgeable at it is outstanding, and the stage where a
   defect is first judgeable is the cheapest place to fix it. *Reverse-if:* the next first-contact
   re-measure shows authors treating "clean" as final and shipping a re-raised earlier-stage code.
   Then the stage line names the re-raised codes explicitly (a card, not this one). (Red-team
   round 1 moved `W_FLOOR_UNASSIGNED` walls → openings, `W_ROOM_NO_CLEAR_PATH` openings → fixtures
   and `W_ROOM_TOO_NARROW` rooms → walls, from the first draft's "latest stage the check needs".)
3. **The per-rule table (53 codes): rooms 5, walls 4, openings 22, fixtures 16, drafting 6, brief
   0.** `test/stages.test.ts` pins every code. The drafting layer is exactly the drafting stage, so
   the ADR 0032 layer and the stage never disagree.
   - rooms: `W_ROOM_TOO_SMALL`, `W_GARAGE_TOO_NARROW`, `W_ALIAS_MATCH`, `W_STAIR_UNMATCHED`,
     `W_OUTDOOR_OVERLAPS_ROOM`.
   - walls: `W_ROOM_NOT_ENCLOSED`, `W_BOUNDARY_NO_WALL`, `W_ROOM_OUTSIDE_SHELL`,
     `W_ROOM_TOO_NARROW`.
   - openings: everything that reads the door graph or an opening: reachability, entrance,
     privacy, the opening and door-geometry rules, daylight (`W_BEDROOM_NO_WINDOW`,
     `W_HABITABLE_NO_WINDOW`, `W_ROOM_NOT_EQUATOR_FACING`), the walk (`W_PATH_TOO_NARROW`,
     `W_CIRCUITOUS_PATH`), `W_SWING_OBSTRUCTED`, `W_LEAF_ACROSS_DOORWAY`, `W_BALCONY_NO_DOOR`,
     `W_FLOOR_UNASSIGNED`.
   - fixtures: every furniture, fixture and clearance rule, plus `W_ROOM_NO_FIXTURE`,
     `W_ROOM_MISSING_DEFINING`, `W_DOORWAY_BLOCKED` (silent without furniture) and
     `W_ROOM_NO_CLEAR_PATH`.
   - drafting: the six annotation-family codes.

   *Reverse-if:* per code, as in decision 2. A new rule adds its row to the test's table, so the
   stage is reviewed with the rule.
4. **Intent assertions take their stage from their predicate, not from the brief's suggested
   mapping where the two differ.**
   - The room count, named rooms, room areas and total area are `rooms`.
   - Room dimensions and exact sizes (`roomDimensions`) are `rooms`, not `walls`. They are
     measured on centrelines, the room's own `size` (PS4.4), so the fact exists once the room does.
   - The gross internal area is `walls`: it is read inside the exterior walls' inner faces, and a
     plan with no walls has none (`E_INTENT_UNMEASURED`).
   - Adjacency and reachability are `openings`, not `rooms`. ArchLang's adjacency is
     interior-door adjacency ("Connect them with an interior door"), so at `rooms` it would fail
     on every plan without doors, and a brief with adjacency could never have a clean `rooms`
     stage.
   - Window counts (`E_INTENT_NO_WINDOW`, `E_INTENT_NO_SITE`) are `openings`.
   - `E_INTENT_UNMEASURED` takes its predicate's stage. For a bare code (`codeStage`),
     `INTENT_CODE_STAGES` gives each intent code the earliest stage its predicate can be judged at
     (`E_INTENT_UNMEASURED` is `rooms`, since it can come from a room dimension). A violation
     always carries its predicate, so `--stage` reads `predicateStage`.
   - Under `--stage`, the intent block's `violations` and `measures` follow the stage. Its
     `satisfied`, `total` and `subscores` stay the whole brief's meter, and `at_stage.intent`
     gives the staged `{ satisfied, total }` over the assertions of stage ≤ s (red-team round 1:
     filter consistently, and carry the staged counts in `at_stage`).
   - A `--graph` check reads the door graph, so it is `openings`. Before that stage its block is
     left out and a mismatch counts as one held-back finding.

   *Reverse-if:* the intent channel gains a shared-edge adjacency (rooms that touch, without a
   door). Then that assertion is `rooms`.
5. **A keep's stage is the stage of its measure** (ADR 0033).
   - `min clear` measures between wall faces and `on axis` names a wall, so both are at least
     `walls`.
   - Every other form takes the latest stage among its targets: a room's datum or an axis is
     `rooms`, a wall segment is `walls`, and a bare id takes its element's kind
     (`ELEMENT_KIND_STAGES`: stair, void and outdoor are `rooms`; column, roof and fence are
     `walls`; opening kinds are `openings`; furniture is `fixtures`).
   - A broken hard keep's `W_KEEP_VIOLATED` is matched to its keep by (file, span, storey). A keep
     is refused in a component body or an imported file (`E_KEEP_PLACEMENT`), so its warning has
     no `file`; one with a `file` matches no keep and falls back to `codeStage`.
   - A broken soft keep (a `next` intent item) is held back with its stage. Keep rows are
     readings, not findings, and are printed whole.

   *Reverse-if:* a keep form whose measure reads something its targets do not name.
6. **Compile-channel diagnostics map by code family; errors are never held back.**
   - Compile warnings are listed one by one in `COMPILE_WARNING_STAGES`, and the test derives the
     list from the catalogue. Language and deprecations are `brief`, `W_ROOM_OVERLAP` is `rooms`,
     off-wall openings and `W_SWING_ROOM_NOT_ADJACENT` are `openings`, and style, fonts, label
     anchors, dimensions and scale are `drafting`.
   - Errors map by prefix family, for the reader. They are always shown, because a plan that does
     not resolve has no clean stage.

   *Reverse-if:* none planned. An error held back would let a non-resolving plan read as clean.
7. **Taste never gates and is reported only at `drafting`**, so below `drafting` the taste tier of
   `next` is empty. `clean` is "no tier of `next` but taste has an item", which is the moment to
   advance. Taste is a reviewer's tool (D20).
8. **The `stage` key is CLI-side enrichment, on `validate --json` only.** `diagnosticToJson`, the
   library `lint()` and `lint --json` are untouched, so ADR 0032's digests and every `lint()`
   consumer see nothing new. The key is the last key of each object, so it is additive: PS5.3's
   `next` law (`cli-validate-next`) holds unchanged.
9. **The digest laws that hash `validate --json` (K1 `keep-byte-identity`, K3 `keep-digests`)
   strip the new key rather than re-pin**, following the PS7.6 pattern. `test/validate-json-run.ts`
   adds `withoutStageKeys`, which removes a string-valued `"stage"` key only when it is the last key
   of its object, and `validateDigestView` = `withoutStageKeys ∘ withoutSummary`. The two
   measurement bodies (`keep-weak-law.ts`, `keep-harness.ts`) apply it. No digest value was edited,
   and K1 and K3 are green with their old pins.
10. **`--stage` with no value exits 3** (`--stage needs a value: …`), never read as no flag, as PR
    #279 does for `context --level`. `parseArgs` is not changed (#279 changes the same line);
    `cmdValidate` reads the key's presence.
11. **MCP `validate` tool: not changed.** Changing it needs a `packages/mcp` version bump (iron
    law), so it waits for PS5.3a's bump. A follow-up can pass `stage` through to it.

## Evidence

- **Default unchanged, byte for byte.** Against `origin/main@52e7c71f`, built in a second worktree,
  the comparison covered `validate --json`, `validate --json --strict`, `validate`,
  `validate --strict`, `lint --json` and `lint` over all 180 files (34 examples, 146 defect-corpus
  plans): 1080 runs. With the `stage` keys stripped from `validate --json`, stdout, stderr and exit
  code are identical in all 1080. 0 differ; 340 `stage` keys were stripped. `lint --json` is
  identical raw.
- **The keys added without `--stage`**: `diagnostics[].stage` and `intent.violations[].stage` (the
  latter only with `--intent`), each appended last. Nothing else.
- **`--stage` over every example, at every stage** (`test/stages.test.ts`):
  - The shown diagnostics are exactly the errors plus the warnings of stage ≤ s.
  - `held_back` is the rest, `summary` opens with the stage, `next` is of a shown stage, and
    `clean` equals `next === null`.
  - At `drafting` nothing is held back.

  Per example (shown/held back), the examples with any diagnostic:

  The other 27 examples have no diagnostic at any stage. The defect corpus has 146 plans and 155

- **`--strict --stage` gating.**
  - A rooms-only plan with a WC under 1.1 m² exits 2 under `--strict --stage rooms`.
  - With the WC grown to 1.2 m² it exits 0 at `rooms` (`ok`, `clean`, later-stage findings held
    back), and exits 2 under plain `--strict` and under `--strict --stage walls`.
  - Errors are never held back: a fixtures-family error (`E_FURN_SIZE`) shows at `brief` and at
    `rooms`, with `ok` false, exit 2, `next` the error and `clean` false.
  - `--stage` with no value, or an unknown stage, exits 3.
  - A window assertion is held back at `rooms` (intent `ok`, exit 0) and fails at `openings`.
  - A `--graph` block is absent at `rooms` and gates at `openings`.
  - Taste, on `bungalow` (whose plain `--taste generic` `next` is a taste item): `next` is `null`
    and `clean` true at every stage below `drafting`; at `drafting`, `next` is plain `--taste`'s
    taste item and `clean` is still true (taste never gates).
  - `--intent` with a gross internal area and a room width: at `rooms` only the width's measure
    row and violation are shown (`at_stage.intent` 0/1); at `walls` both (0/2). The intent
    block's `satisfied`/`total` equal the plain run's.
  - The text report prints the `stage <s>: …` summary line under `--graph` too, and the stage line.
- **Corpus movement: none.** No rule body changed, and every `lint()` digest, `describe()` and SVG
  is untouched. `eval/judge-fixture.json` is untouched.
- **Spec length: 29,931 UTF-16 units** (cap 30,000; it was 29,822). The clause cost 109 units and
  leaves 69.

## For the PR that merges second (collision prep)

`LintRule.stage` is required, and `test/stages.test.ts`'s `DECIDED` table pins every code. A PR
adding lint codes therefore adds `stage` to each new rule and the codes to `DECIDED`, and updates
the per-stage count assertion. The two lint PRs in flight:

- **#280 (PS2.11e stairs):** `W_STAIR_TOO_STEEP`, `W_STAIR_HEAD_VOID` and
  `W_SHAFT_FOOTPRINT_MISMATCH` → `rooms`; `W_STAIR_NO_LANDING` → `walls`; `W_STAIR_SIDE_ENTRY` and
  `W_SWING_OVER_STAIR` → `openings`.
- **The PS2.11e clearance PR:** every `W_HOB_*` code → `fixtures`; the wide-leaf code →
  `openings`.
