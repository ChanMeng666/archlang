**状态：** 已规划，未开工，代码零改动。MF-D1、MF-D2 已于 2026-11-10 委托裁定（§6.1、§6.2），其余裁定待定。卡号 MF13 空缺；MF2、MF4、MF9 已并入别处，MF7 已撤回（`cards.md`）。基线是 `main@3db2d7a8`（core 1.57.0）。卡片见 `cards.md`，恢复点见 `handoff.md`。

## 1. 现状：ArchLang 的数学与技术原理（2026-11-10 核对）

### 1.1 2D 核心：五层，地基没变

| 层 | 是什么 | 代码 |
|---|---|---|
| 0 地基 | 平面直角坐标系，单位毫米，原点左上，+x 向右，**+y 向下**。房间是"左上角 + 宽高"，墙是一串点，`grid` 吸附 | `docs/agents/architecture.md` § Conventions；`examples/studio.arch` 全是坐标写法 |
| 1 少写坐标 | 结果仍是普通坐标。分三种写法：`let` 变量与表达式（Pratt 解析器 + 步数计量）；相对定位 `right-of … align … gap`，按拓扑序逐个算闭式加减，**不用优化器**；`walls from rooms` 扫描房间边，单侧有房间的是外墙，两侧都有的是隔墙，只用 `===`/`<`；唯一例外是 1e-6 mm 的环尘阈值 `RING_DUST_MM`（`src/room-tiling.ts`） | `src/expr.ts`、`src/layout.ts`（ADR 0004）、`src/room-tiling.ts`（ADR 0028）；示例 `examples/knob-flat.arch` |
| 2 画准 | 墙带是中心线 ± 半厚，转角斜接；墙体拼接求出各墙带的交点，只保留"一侧是墙"的边；多边形面积用鞋带公式，点是否在内用射线法；弧墙用极坐标（圆环扇形）。全部是闭式运算，不迭代到容差 | `src/geometry/band.ts`、`joinery.ts`、`intersect.ts`、`polygon.ts`、`arc.ts`、`arc-band.ts` |
| 3 算数据 | 面积：中心线面积；净面积 = 房间 − 墙带并集，用格林公式；GIA 是外墙内表面围合的面积。通行：栅格上做 BFS、最宽瓶颈、距离变换。lint：`src/lint/rules/` 下 22 个规则模块，共 61 个 `LintRule` | `src/analyze/net-area.ts`（ADR 0027）、`gross-area.ts`、`nav-grid.ts` |
| 4 保证一致 | 几乎不加功能，只保证前面几层在旋转、镜像、换引擎时答案不变。D4 对称群（8 种直角对称，2×2 整数矩阵，元素取 −1/0/1）；四个可选半环（布尔、min-plus、max-min、字典序）共用一个广义 Dijkstra；审美评分和最小外接矩形用 0.001 mm 整数格点加 `BigInt`；步数预算与 `MODEL_RANGE_MM`（2²⁵ mm） | `src/algebra/d4.ts`、`semiring.ts`、`paths.ts`（ADR 0020）；`src/taste/arith.ts`、`src/geometry/min-rect.ts`、`src/num-format.ts`（ADR 0022） |

第 4 层每一项都是先出了真实缺陷、复现之后才加的（ADR 0020 列了 5 类，ADR 0022 列了更多）。它的代价是代码量和贡献门槛上升；用户和写 `.arch` 的 AI 都看不到这一层。

> **更正（同日对话中的口误）：** 对话里曾说"lint 有 23 条规则"，不准确。准确数字是 22 个规则模块、61 个 `LintRule`（`grep -r "LintRule = {" src/lint/rules | wc -l`）。

### 1.2 3D：独立的下游包，是 2.5D 拉伸，不是自由建模

依据是 ADR 0030 和 `packages/archlang-3d/src/`。

- **位置**：`@chanmeng666/archlang-3d` 是独立包。核心不依赖它，也不为它画任何东西。它通过 `resolvePlan` 读取核心已经解析好的数据（ADR 0031）。墙的占地来自核心的 `joinWallSet`，3D 包不另写一套墙体拼接。
- **流水线**：`.arch` → `resolvePlan()` → `Scene3D`（平面轮廓 + 高度区间，整数微米）→ `Mesh3D`（三角网格）→ 回放查看器（three.js）或 GLB（glTF-Transform）。
- **坐标**：Scene3D 沿用平面轴，x 向右、y 向下，再加 z 向上；毫米 ×1000 只舍入一次（`src/units.ts`）。导出时固定换成 glTF 轴：X = 平面 x，Y = 上，Z = 平面 y（`src/mesh/types.ts`）。
- **核心运算是拉伸**（`src/mesh/extrude.ts`）：把平面多边形从 z₀ 拉到 z₁，得到棱柱。楼板 200 mm（默认值）、地面饰面 5 mm、墙、柱都是这样做出来的。顶面和底面用 earcut 三角剖分（不加点），每个面的法向在数值上逐一校正为朝外，每个壳体必须封闭且体积为正（`src/check/verify.ts`，V-GEO-02）。3D 包里**没有任何三维布尔运算**，门窗洞在核心的 2D 拼接里已经挖好了。
- **几个公式**：
  - 弧线细分，弓高 ≤ 2 mm：Δθ = 2·arccos(1 − ε/r)，n 取 4 到 720（`src/curves.ts`）。
  - 楼梯第 k 级高度 = z₀ + round(rise·k/R)（`src/mesh/stair.ts`）。
  - 重叠地面依次抬高 0.5 mm，避免 z-fighting（`src/scene3d/overlap.ts`）。
  - 相机用 lookAt 叉乘（`src/replay/camera.ts`）。
- **家具**：参数化生成器，精确贴合平面图上的占地；除少数 `handed` 家族外都左右对称（`src/mesh/t0*.ts`）。挂墙家族用 `mountMm` 定高度：`mirror`、`whiteboard`、`upper_cabinet`、`urinal`、`range_hood`、`towel_rail`，另有 `tv` 用 `hungFromTop`（`t0.ts`），这些高度都是 ADR 0030 规定的 3D 账本默认值。（对话中说成"三个"，是照抄了 `t0-utility.ts` 一个批次文件的头注释，已更正。）
- **渲染**交给 three.js；Blender 只作为 GLB 之后的外部渲染器。平面没有写明的值全部进 `assumptions[]` 账本（ADR 0005）。产出物要和平面逐项对账，并通过 Khronos glTF-Validator，0 错误 0 警告。

### 1.3 高度在今天的位置（§3、§4 都建立在这里）

- 核心有高度基准：层高 3000、门顶 2100、窗台 900、窗顶 2100（`src/datum.ts`）。**"Heights draw nothing"**：写了高度只会进 `describe()` 和 Plan JSON，不改动任何一笔绘图。核心**没有楼板厚度**，原文是 "Deferred by name"。
- 家具**没有高度**，目录注释原话是 "The catalogue holds no heights"。目录只有一个三值的剖切层 `underlay | body | overhead`（`src/fixtures-catalog.ts:909`）。两件家具只有在同一层时才可能相撞。
- 剖切面以上的 overhead 家族共 4 个：`upper_cabinet`、`wall_cabinet`、`mirror`、`range_hood`，都是 `requiresWall`（`test/overhead-furniture.test.ts` 钉住这一点）。约定是"虚线 = 在剖切面以上"（backlog 5.5）。
- 3D 包有自己的 200 mm 楼板，所以天花 = 上层标高 − 200（`mesh/build.ts:367`）。这和核心"没有板厚"并不一致。2026-11-06 的 `31739be3` 已经让上层楼板下的墙和柱停在板底（账本 `stops-under-slab-above`），所以墙板重叠**已经修好**。没有上层的情况（单层，或顶层）不做截断。

## 3. 悬空物、挂顶物、窗帘（对话第 4 问）

### 3.1 问题的本质

难点不在"怎么画"，而在于**家具没有高度这一维**。吊柜、搁板、吊灯、窗帘都是由"挂多高、从哪里挂"来定义的。

现有地基见 §1.3：三层剖切模型、虚线约定、4 个 overhead 家族，以及 3D 的 `mountMm`。缺口有四个：

1. 作者没法写"挂在 1500 mm"。注意这是**两个不同的问题**：
   - backlog 5.5 问的是"怎样说'画在剖切面以上'（虚线）"，它列了三种做法（furniture 子句、类别属性、平面级约定），5.7 已经提供了语义。
   - "挂墙"不等于"在剖切面以上"：`urinal`（350）、`towel_rail`（200）、`whiteboard`（900）都挂墙，但都不是 overhead，也不画虚线。所以 `mount <mm>` 只能是纯数据，不能决定虚线。
2. 没有挂顶类家具（吊灯、吊扇、投影仪）。
3. 没有窗帘。
4. 离散的三层回答不了数值问题，比如"吊柜底 1400 会不会挡住窗顶 2100"。

backlog 5.5 预埋了一个绊线：`test/overhead-furniture.test.ts` 钉住"overhead 一律 requiresWall"。**第一个挂顶家族出现时，这个测试应该故意变红，然后补上 `W_FURN_CLEARANCE` 的 overhead 分支，不能删测试**（5.5 原文："Deleting the pin instead of adding the arm is the failure mode."）。

### 3.2 数学：平面形状 × 高度区间

每件家具 = 一个 2D 占地 × 一个 1D 区间 [z₀, z₁]：

| 支撑方式 | 例子 | 区间 |
|---|---|---|
| 落地 | 沙发 | [0, h] |
| 挂墙（背靠墙面） | 搁板、吊柜 | [mount, mount + h] |
| 挂顶（从天花往下） | 吊灯、吊扇 | [天花 − drop − h, 天花] |
| 挂窗（宿主是窗） | 窗帘 | [地面或窗台, 轨道高] |

> **相撞 ⇔ 占地相交 且 区间相交**（区间相交就是 `a₀ < b₁ ∧ b₀ < a₁`，精确且确定，不需要三维布尔，也不需要碰撞引擎。）

现有三层模型是这个模型的粗粒度版本，可以平滑升级：

- **绘图只看"剖切层"，不看数字，也不看"挂墙"。** "Heights draw nothing" 不变。虚线只由"在剖切面以上"这一分类决定：类别自带（今天的 4 个 overhead 家族、将来的挂顶家族），或者由 5.5 将来给出的显式写法决定。`mount` 的数值和"写没写 `mount`"都不影响绘图。
- lint 和 `describe()` **只读作者写出的高度**，和现有先例一致：`isFloorLength` 只认作者写出的 `sill 0`。没写高度的家具，核心不报区间，也不触发区间检查。家具的默认高度按 ADR 0030 留在 3D 账本里，核心目录不承载默认高度。旧图逐字节不变，每种新写法都要配一条字节恒等律测试。
- **通行分析不用升级成 3D**：栅格只把"底边低于人体净高"的物体当作障碍。今天 `test/overhead-furniture.test.ts` 把 overhead 家具算作两张栅格上的障碍；挂顶物底边未知时，**保持按障碍算**（偏保守），绝不猜它可以通过。

由此可以做的 advisory 检查。前提是相关高度由作者写出；阈值要写明来源，带 `[S]` 的是二手来源，进代码前要读原文：

| 检查 | 数学 | 参考值 |
|---|---|---|
| 吊柜挡窗 | 同一面墙上，沿墙区间相交，并且 [柜底, 柜顶] 与 [窗台, 窗顶] 相交 | 窗台 900、窗顶 2100（`src/datum.ts`） |
| 吊柜与台面的间距 | 两个区间之间的间隙 | 常见约 450 mm（18 in），范围约 380–500 `[S]` |
| 门扇扫到挂墙物 | 门扇扫过的扇形 × [0, 门顶] 与挂墙物的区间相交 | 门顶 2100 |
| 吊灯碰头 | 位于通行区时，灯底 < 约 2000 | 账本默认值 |
| 餐桌吊灯高度 | 灯底 − 桌面 | 常见 28–36 in，约 710–910 mm `[S]` |
| 窗帘被挡 | 拉开后的堆叠区间与窗前家具相交 | 每侧堆叠约 150–300 mm `[S]` |

现有的 `W_FURNITURE_OVER_WINDOW` 和 `isLowUnit`（`src/lint/clearance-measure.ts`）已经在用"窗台为 0 的落地窗"这条高度事实，新检查是同一思路的推广。

### 3.3 2D：分图表达是行业做法

| 图 | 表达什么 | 现状 |
|---|---|---|
| 平面布置图（剖切高度约 1.2 m，向下看） | 落地家具画实线；剖切面以上的吊柜和搁板画虚线；窗帘在窗内侧画波浪线（室内图常见画法 `[S]`，GB/T 50001/50104 原文未核对） | 虚线约定已有；自定义悬空物和窗帘没有 |
| 顶面布置图（RCP） | 吊灯、吊扇、窗帘盒、吊顶 | 没有 |
| 立面图、剖立面 | 挂墙物和窗帘的高度关系 | 见 `../drawing-set/`（DS 卡片） |

**RCP 在数学上的好消息**："反射"天花平面是把地面当镜子去看天花，方向和平面图**完全相同**，所以平面坐标可以直接复用，不需要任何镜像变换。新增成本主要是一套顶面符号。

**约束**：2026-11-06 的 roadmap §4 列明"不做灯具/照明图层、luminaire schedule"。RCP 和挂顶家族因此需要所有者重新裁定（MF-D2、MF-D7）。

### 3.4 3D：每类物体一种确定的造型方法

所有造型都满足 3D 包现有的规则：壳体封闭、逐字节确定、默认值进账本。并且**刻意全部做成竖直棱柱**，这样它们自动满足 §4 剖面算法的前提。

- **搁板、吊柜**：背面贴墙的内表面（核心 `flush` 已经能给出），在 [z₀, z₁] 区间拉伸。现有挂墙家族已经这样做，只需改高度来源：作者写的值优先于类别默认值。
- **吊灯、吊扇**：
  - 先要定义"天花"。核心没有板厚，3D 包有 200 mm 板厚，两边不一致。吊灯一旦参与 lint（碰头检查），核心就需要净高，也就是需要被点名推迟的楼板厚度。这与 roadmap RM6.1 的"楼板构造 datum"是**同一件事**（MF-D1）。
  - 造型：吸顶盘 + 吊杆或吊线（细棱柱）+ 灯罩。灯罩是旋转体，用固定 16 边形叠层近似（3D 包已有固定 16 边形表）。
  - 关系写法 `above <table>` 时，位置取桌子**形状自身的对称中心**。L 形桌这类没有唯一答案的形状直接拒绝，不能用包围盒或质心（AGENTS.md："A derived position comes from the shape"）。
  - **只做几何，不发光**，与 roadmap §4"不做光影"一致。
- **窗帘**：
  - 宿主是窗，就像门的宿主是墙。轨道宽 = 窗宽 + 两侧堆叠宽；轨道高取"贴天花"或"窗顶 + 150"，进账本。
  - 褶皱截面用关于轨道中心**偶对称**的曲线，例如 y = A·cos(2πx/λ)，并让波峰数关于中心对称。y = A·sin(…) 是奇函数，镜像后形状会变，违反"符号不得获得手性"和"3D 生成器左右对称"两条规则。截面竖直拉伸成形，再向两侧各偏移半个布厚，形成封闭薄壳，可以通过 V-GEO-02。
  - 布料展开长度一般约为轨道宽的 2 倍（褶皱倍数）。展开长度就是正弦曲线的弧长，涉及椭圆积分，没有初等闭式解。按项目"不迭代到容差"的规则，**预先算好一张整数表（倍数 → A/λ），运行时只查表**。
  - 开合状态像门一样进账本（默认合上）。纱帘用半透明材质槽（glTF `alphaMode: BLEND`），这个槽必须先加进核心的 `FIXTURE_MATERIALS`（`.claude/rules/archlang-3d.md`）。
  - `curtain on <window>` 是一个**元素模块**（`src/elements/`，在 `defs.ts` 注册），不是 `FIXTURE_FAMILIES` 的一行。
  - Blender 的窗帘插件也用频率、幅度、偏移这组参数，说明参数化方向和行业做法一致 `[S]`。
- **回放**：俯视阶段挂顶物会挡住平面，所以要隐藏。屋顶在整段回放中一直隐藏（`src/replay/timeline.ts`）；挂顶物是在相机抬起后重新出现，还是像屋顶一样一直隐藏，在 MF14 里决定。

### 3.5 语法草案（仅供讨论，需裁定 MF-D3）

```text
furniture shelf against r_live.left offset 1200 size 900x250 mount 1500
furniture pendant above t_dining drop 760
curtain on w_living track ceiling stack 200 state closed
```

`mount` 和 `drop` 只是高度数据，**不画任何东西**。虚线由剖切层决定（见 §3.2），不由挂墙决定。这三种写法都是语言新形式，按 roadmap 规则都带 `[语法]`，并依赖 PS7.9 先给 `spec.llm.md` 腾出空间（它已用 29,695/30,000，上限是铁律）。

## 4. 剖面图的铺垫（对话第 5 问）

### 4.1 已有方案：Band Envelope（`../drawing-set/research/2026-11-02-section-elevation.md`）

- 实测 36 个示例、4807 个实体，**全部是"平面多边形 × [z₀, z₁]"**。
- 算法分三步：把所有 z₀/z₁ 排序、去重，切成高度带（同一带内场景不随 z 变化）；每带只剩一个 2D"沿视线找最近线段"的问题；相邻格子的标签不同就出线（剖到的、投影的、共面消失）。
- 视图坐标：u = −dy·x + dx·y，深度 d = dx·x + dy·y − c。全程只用整数微米和四则运算，无容差。探针 125 行，全语料约 0.7 秒。
- 研究报告列出的必做项：交叉细化；弧墙平滑抑制（夹角 < 12°）；剖切分级（结构填充，门窗不填，家具默认不进）；5 mm 面层不进视图。
- 剖面放在 `packages/archlang-3d`，核心只画平面上的剖切符号（DS11）。

**需求证据**：外部用户 gerontec 只用 `describe --json` 等公开输出，自己写了剖面工具 `gerontec/archlang-section`（#532，已关闭），并指出缺两样东西：楼板构造层、平面剖切线元素。这就是 roadmap RM6.1（批次 D 首位）。另一个直接相关的开放 issue 是 #681：`walls from rooms` 的墙没有坐标输出，下游工具只能自己重新推导墙。

### 4.2 前面的建议与剖面的关系

**A. 直接前置（不做，剖面就不对）**

| 建议 | 关系 |
|---|---|
| §3.2 区间模型 | Band Envelope 的输入格式就是 `polygon × [z₀, z₁]`。家具有了真实区间，才能出现在剖面投影层的正确高度上 |
| 楼板构造 datum（MF-D1 = RM6.1） | #532 点名的缺口：剖面要画对板厚和标高，就得有作者写的楼板数据，不能用 200 mm 常量。研究报告 §4.4 记录的墙板重叠，已经在 2026-11-06 由 `31739be3` 修好（墙、柱停在上层板底），对话中把它说成"现存缺陷"是读了旧研究、没核对代码，已更正 |
| F3 统一格点（= RM1.5b） | Band Envelope 的确定性依赖整数输入。核心在 resolve 出口就统一成格点，剖面读到的每个坐标在构造上就是确定的 |

**B. 让剖面更专业**

| 建议 | 关系 |
|---|---|
| F4 墙体分层 | 剖面最能体现专业性的是墙身构造（结构填充、保温图案、饰面细线）。剖切处每一层都是"一段 u 区间 × 一种材料"，格子标签天然支持，算法不用改 |
| DS3 外表面面积 + F5 面积标准 | 有了层高和板厚，就能执行 GB/T 50353-2013 的"结构层高 2.20 m 及以上计全面积，以下计 1/2"（`[S]`，原文待读）。剖面和面积表得出同一个结论 |
| F6 上下层对位（`keep stacked`） | 剖面就是把上下层切开对着看。先用 `keep stacked` 把需要贯通的东西锁住，剖面就不会画成一张"暴露问题的图" |
| §3.4 造型 | 灯罩叠层和窗帘的波形截面都是竖直棱柱，不会打破算法前提 |

**C. D4 等变定律可以测剖面**

四个看向是 D4 的旋转。等变预言机（`test/helpers/d4-oracle.ts`）可以扩展出一条定律：**先镜像平面再剖 = 先剖再镜像剖面**。研究报告提醒过"u 的公式写错就是镜像图纸，而且错得隐蔽"，这条定律能自动抓住这类错误 → 卡 MF18。

**D. 有理数旋转让斜剖保持精确**

研究报告的 V2 方案是"旋转后舍入到整数微米"。另一种做法是只允许 cos 和 sin 都是有理数的方向（勾股数，比如 3-4-5 对应约 36.87°）：旋转后乘以分母，坐标仍是精确整数，**不需要舍入**，拓扑也不会因舍入而裂开。这样的方向在圆周上处处稠密，可以把任意方向逼近到 0.001 mm 以内。**代价**：微米坐标最大到 2²⁵ mm × 1000，再乘上逼近所需的分母，会超过 2⁵³，必须用 `BigInt`，这和 DS13"只用 number 四则"的规则冲突。MF20 必须在这两者之间给出取舍 → 卡 MF20，裁定 MF-D6（与 P3-7 的搁置有关）。

**E. 与剖面无关的（如实记录）**：F1 精确净宽、F2 可见性图属于平面通行分析。RCP 同属 2D 图纸体系，可以共享符号和线宽，但与剖面的几何无关。

### 4.3 任何计划都还没覆盖的缺口

1. **斜向的东西会打破"竖直棱柱"前提**：楼梯梯段、坡屋顶（今天 `Roof.form` 只有 `"flat"`）、坡道。建议把"棱柱"推广为**"沿任意轴拉伸的棱柱"**：竖直棱柱沿 z 拉伸，楼梯沿梯宽拉伸（DS15 的"横向棱柱"），单坡屋面沿屋脊拉伸。视线与拉伸轴平行时，投影是一个多边形，Band Envelope 照样适用。这样楼梯和屋顶是同一种数学对象 → 卡 MF17。
2. **竖向尺寸链和标高符号**：核心的尺寸线只在平面方向。剖面需要竖向尺寸链（层高、窗台、窗高、总高）和标高（±0.000）。应复用 `dims auto` 的排布思路和 `num-format.ts`；高度算法按 DS14 的要求读 GB 55037-2022 → 卡 MF19。
3. **室外地坪**：DS12 已经计划加 `meta.groundZ`。
4. **室内剖立面是另一种产品**：建筑剖面默认不画家具；室内剖立面恰恰要画吊柜、搁板、窗帘。§3.2 的区间模型就是它的基础，用同一个算法、换一套分级即可。**先确认网友要的是哪一种**（§6.0 信号）。

### 6.1 MF-D1 裁定：核心引入楼板构造 datum（2026-11-10）

**裁定方式：** 所有者 2026-11-10 原话（译自中文）："请你帮我做出最佳决策，记录到相关文档中。" 这是对当天这两项的委托，不是长期委托。所有者一句话即可推翻。本裁定不改任何铁律。

**决定：** 采纳 roadmap 卡 RM6.1 的既定设计，不另起一套。唯一的增补是 MF-D11（顶层和单层的天花），它需要第二个数，提案在 RM6.1 的 PR 里给出，由所有者裁定。具体如下。

1. **只进数据，不画任何东西。** 这个 datum 只进入 `describe().heights`（以及 Plan JSON 已承载的高度字段），SVG、PDF、DXF 一笔不动。"Heights draw nothing" 原样成立。
2. **没写就不报，不猜。** 全图**一层楼板都没写**时，`describe()` 一字不变：不输出板厚和净高，也不加跳过说明。只有至少一层写了楼板时，没写的层才在"跳过了什么"里注明。字节恒等律按这个形式写：一层楼板都没写的图，SVG、`describe()`、`lint()` 三处都逐字节不变。（第一版的写法会让已经写了 `height` 的示例多出一条跳过说明，自相矛盾，已更正；RM6.1 卡里也有同样的张力，在它的 PR 里按这个形式落地。）
3. **语义（推荐，在 RM6.1 的 PR 里定稿）：**
   - 子句挂在 `level` 上，表示"本层楼面之下的楼板构造总厚"，含面层。这和 #532 的用法一致：那里写的是"concrete slabs 0,32 m including floor finish"。
   - 第 n 层净高 = 第 n 层的 `height`（楼面到楼面）− 第 n+1 层的楼板厚。
   - 顶层上方是屋面构造，本 datum 不覆盖，所以顶层净高不报，并注明原因。**这留下一个缺口**：单层平面只有顶层，所以根本得不到天花。#532 的房子本身就写了顶层净高（OG 2,34 m），这个语义表达不了。这个缺口记为 MF-D11，必须在 RM6.1 的 PR 里解决（给出顶层的天花来源）。在那之前，MF14 被它阻塞。本条的意思不是收窄 RM6.1 "每层净高 = 层高 − 楼板"的范围，而是指出顶层需要第二个数。
   - 子句的拼写由 `gen:*` 闭集决定；候选 `slab <mm>`，结构层和面层是否分开写留给 PR。
4. **天花和挂顶物用它。** 挂顶家族（MF14）的悬挂基准 = 净高。得不到净高时（没写楼板，或 MF-D11 未解决的单层和顶层），碰头检查**跳过**，并给出 coverage 原因（如 `no-ceiling-datum`），绝不拿默认值去猜（ADR 0005）。通行栅格上，这类挂顶物仍按障碍算（§3.2）。
5. **3D 包：**
   - 写了楼板时，读作者写的值，代替 200 mm 默认值；`31739be3` 的"停在板底"规则改用这个值。
   - 没写时，保留账本里的 `slab-default-200`，laneway 的 Mesh3D/GLB 固定哈希不动。

**排期不变：** RM6.1 仍是批次 D 首位，在冻结期之后，不提前。剖面本体（DS13）仍按 drawing-set 的 D3 排期。

**为什么：**
- 它是两条线（剖面、挂顶物）共同的前提；挂顶物另外还需要 MF-D11。外部用户（#532）已经明确要它。growth 同日调研的 62 条规则里，有 8 条也等着它。
- 它不画任何东西，所以和"平面优先"、"高度不画"两条原则都不冲突。
- 不写就不报，旧图零变化，回退成本几乎为零。
- 反过来，如果不做，3D 的 200 mm 常量和核心"没有板厚"会继续各说各话，剖面上的板厚和标高也只能画成默认值。（第一版这里还拿"墙板重叠"当理由，但那个问题 11-06 已经修好，已删去。）

**推翻条件：** RM6.1 实施时，如果发现单一总厚说不清 #532 那类真实剖面（例如必须区分结构层和面层才能画对标高），就改成分开写的两个数，并回到这里记一笔。

### 6.2 MF-D2 裁定：挂顶物和窗帘作为物体做，照明不做（2026-11-10）

**裁定方式：** 同 §6.1，委托裁定，所有者一句话即可推翻。

**决定：**

1. **允许**新增挂顶家族（吊灯、吊扇、投影仪等）和窗帘，身份是**物体**：
   - 有占地、高度区间、平面符号、3D 几何，参与碰撞和净空检查；
   - 挂顶家族照规矩走 `FIXTURE_FAMILIES` + `CATALOG` + 3D T0 生成器，绘制的符号忽略 `label`；窗帘是元素模块（§3.4）。
2. **照旧不做**：照明图层、灯具表（luminaire schedule）、照度或光影计算、3D 中让物体发光。roadmap §4 的"不做"清单保留这些内容，只改写那一行的措辞，把"物体"和"照明"分开。
3. **RCP（MF-D7）不在本裁定范围内**，仍待裁定。在那之前，挂顶物只出现在平面（剖切面以上的虚线约定）、`describe()` 和 3D 中。
4. **顺序：** 语法形式仍待 MF-D3。MF14（挂顶）还依赖 RM6.1 和 MF-D11；MF15（窗帘）不依赖楼板，但和 MF12 共用 MF-D3 的语法裁定。所以本裁定只解除"范围"上的阻塞，不解除"语法"上的阻塞。

**为什么：**
- 11-06 那一行反对的是"照明这门专业"（只有一条回复提出，且核心不画灯光）。吊灯作为一个会碰头、会挡视线的**物体**，和吊柜属于同一类问题。
- 吊灯和窗帘在 3D 和剖立面里本来就会出现。不让它们成为物体，就只能让 3D 和剖面去猜。
- 把"物体"和"照明"分开，正好守住 roadmap 想守的边界：不做照明设计，不做 PBR 和光影。

**推翻条件：** 如果 MF14 或 MF15 的 PR 发现某个物体离不开照明语义才能说清楚（比如一定要出灯具表），就停下来回到所有者，不扩大范围。

## 7. 证据的薄弱处（照实写）

- 吊灯、吊柜的高度经验值来自厂商和家居媒体（`[S]`），不是规范原文。
- 窗帘在平面图上画波浪线，是室内图的常见做法，没有在 GB/T 50001-2017 或 GB/T 50104-2010 原文里核对到。
- GB/T 50353-2013 的 2.20 m 半面积规则和"外围护结构外表面"口径，取自地方转载文件，原文待读。
- 有理数旋转"稠密且可逼近到 0.001 mm"是数学事实，但没有在本仓库的语料上测过。
- RLVR 论文只读了摘要级信息。
- 2026-11-10 的独立评审（PR #686）发现，第一版有九处与代码或既有裁定不符：F6/F7 违反 D25；墙板重叠早已修好；单层没有天花；跳过说明会动字节；`mount` 和虚线混为一谈；MF2 与 DS3 重复；挂墙家族数量写错；`assert` 违反 T6；窗帘截面有手性。现在的文本已全部更正。教训：引用旧研究报告里的"缺陷"之前，先核对代码。
